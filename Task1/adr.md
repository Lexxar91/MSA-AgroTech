| 1 | Оператор фермы | Получение оповещений о нештатных ситуациях | Система обнаруживает драки, задавливание поросят, болезни и отправляет уведомление в течение ≤5 сек |

# Нефункциональные требования

| № | Требование |
|---|------------|
| 1 | Отказоустойчивость ≥99,95% (достигается через Docker restart: always на Edge и K8s ReplicaSets в облаке) |
| 2 | Время реакции на событие ≤5 секунд |
| 3 | Видеоаналитика работает в реальном времени (мс-задержка) |

| 6 | Современная аутентификация и разделение ролей |

# Решение

## Основной вариант (Гибрид edge + cloud)

- Edge-агент на каждой ферме обрабатывает видео, управляет устройствами, работает автономно.
- Центральный сервер в облаке агрегирует данные, хранит историю, отправляет уведомления через SMS/email-шлюз.
- Интеграция: агент → сервер через асинхронную очередь (RabbitMQ), с буферизацией при потере связи.
- API: REST для мобильного приложения и внешних систем.
- Хранение видео/файлов: в S3-совместимом хранилище (MinIO), в сообщениях передаётся только ссылка.
- Диаграмма C1 прилагается (variant_a.puml).
- Для асинхронной очереди выбран RabbitMQ (а не Kafka), так как объём событий на ферме умеренный, важна поддержка DLQ и маршрутизации, а не экстремальная пропускная способность.

## Альтернативный вариант (Полностью автономный edge)

- Все решения принимаются локально на ферме.
- Синхронизация с облаком раз в 10 минут (только для аналитики и отчётов).
- Облако используется только для исторических данных, не для реального времени.
- Интеграция: данные передаются через периодические синхронизационные запросы (HTTP POST).
- Хранение данных: локальная БД на edge-агенте + резервное копирование в облако.
- Диаграмма C1 прилагается (variant_b.puml).

# Альтернативы

**Почему выбран гибрид (Вариант А), а не полностью автономный edge (Вариант Б)?**

- Вариант Б нарушает требование «реакция ≤5 сек» для централизованного (облачного) мониторинга и SaaS-модели (синхронизация раз в 10 минут). Локальные алерты срабатывают мгновенно, но облачные дашборды будут отставать.
- Вариант Б не подходит для SaaS-модели в будущем (облако не может быть источником данных в реальном времени).
- Вариант Б снижает бизнес-ценность системы: это уже не мониторинг в реальном времени, а просто логгер.
- Вариант А использует проверенные паттерны (асинхронные очереди с буферизацией), что упрощает поддержку.

# Недостатки, ограничения, риски

| Риск / Ограничение | Комментарий |
|--------------------|-------------|
| **Для основного варианта (А)** | |
| Зависимость от брокера сообщений | При сбое очереди возможна потеря событий → решается через DLQ и повторную отправку |
| Сложность развёртывания edge-агента | Требуется унифицированный образ (Docker) и механизм обновления → можно использовать OTA |
| **Для альтернативного варианта (Б)** | |
| Задержка в облачных оповещениях | Синхронизация раз в 10 минут → не соответствует требованию «реакция ≤5 сек» для централизованного мониторинга |
| Невозможность live-дашбордов | Облако не получает данные в реальном времени → теряется бизнес-ценность |
| Риск потери данных при отключении | При длительном отсутствии интернета данные могут перезаписаться при синхронизации |
