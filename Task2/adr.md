# Решение

## Ограниченные контексты

### Edge (ферма)

| Контекст | Отвечает за | Технологии |
|----------|-------------|------------|
| Видеоаналитика | Анализ видео, детекция событий (драки, гибель, болезни) | Python, OpenCV, ONNX Runtime |
| Управление устройствами | Кормушки, поилки, фильтры | Python, MQTT |
| Локальный алертинг | Оповещения на месте (SMS, звук, свет) | Python, WebSockets |
| Локальная очередь и отправка | Буферизация событий, персистентная очередь, доставка в облако | Python, Pika, RabbitMQ (embedded), SQLite WAL |

 ### Облако (только для основного варианта А)

 | Контекст | Отвечает за | Технологии |
 |----------|-------------|------------|
 | API Gateway | Единая точка входа для мобильного/веб-клиента, маршрутизация запросов | Python, FastAPI |
 | Auth Service | Аутентификация, RBAC, управление пользователями и ролями (для Администратора) | Keycloak |
 | Приём событий с ферм | Приём и маршрутизация событий/команд от всех edge-агентов | RabbitMQ (cloud_mq) |
 | Сервис уведомлений | Отправка SMS/Email при нештатных ситуациях | Python, Twilio |
 | Сервис аналитики | Агрегация метрик по фермам, прогнозирование расхода корма, отчёты для SaaS | Python, Prometheus |
 | Хранилище данных | Хранение файлов/видео-фрагментов и исторических данных | MinIO (S3-совместимое) |

 Каждый облачный контекст выделен в отдельный контейнер (см. C2-диаграмму variant_a), так как у них разные зоны ответственности, разная нагрузка и разный жизненный цикл разработки.

## Альтернативный вариант (Полностью автономный edge)

В этом варианте вся логика находится локально на ферме:

- Все микросервисы работают независимо от облака.
- Облако используется только для аналитики и отчётов, синхронизация происходит раз в 10 минут через HTTP POST.
- Нет асинхронных очередей (RabbitMQ/Kafka), так как нет необходимости в реальном времени между фермой и облаком.
- Все события обрабатываются локально, оповещения приходят мгновенно.

### Интеграции:
 Для Основного варианта (А — Гибрид):

- Видеоаналитика → Управление устройствами: gRPC (высокая производительность для передачи метаданных)
- Видеоаналитика → Локальный алертинг: Прямой вызов (мгновенная реакция ≤5 сек)
- Edge-агент → Облако: AMQP (RabbitMQ) — асинхронная очередь с буферизацией.

 Для Альтернативного варианта (Б — Автономный):

- Видеоаналитика → Управление устройствами: gRPC (высокая производительность для передачи метаданных)
- Видеоаналитика → Локальный алертинг: REST (простота и надёжность)
- Локальное хранилище → Облако: HTTP POST (периодическая синхронизация раз в 10 минут)
# Альтернативы

**Почему выбран гибрид (Вариант А), а не полностью автономный edge (Вариант Б)?**

- Вариант Б нарушает требование «реакция ≤5 сек» для централизованного (облачного) мониторинга и SaaS-модели (синхронизация раз в 10 минут). Локальные алерты срабатывают мгновенно, но облачные дашборды будут отставать.
- Вариант Б не подходит для SaaS-модели — облако не может быть источником данных в реальном времени.
- Вариант Б снижает бизнес-ценность системы — это уже не мониторинг в реальном времени, а просто логгер.
- Вариант А использует проверенные паттерны (асинхронные очереди с буферизацией), что упрощает поддержку и масштабирование.

# Недостатки, ограничения, риски

| Риск / Ограничение | Комментарий |
|--------------------|-------------|
| Для альтернативного варианта (Б) | |
| Задержка в облачных оповещениях | Синхронизация раз в 10 минут → не соответствует требованию «реакция ≤5 сек» для централизованного мониторинга |
| Невозможность live-дашбордов | Облако не получает данные в реальном времени → теряется бизнес-ценность |
| Риск потери данных при отключении | При длительном отсутствии интернета данные могут перезаписаться при синхронизации |
| Отсутствие масштабируемости | Каждая ферма — изолированный остров, сложно внедрять новые функции централизованно |
